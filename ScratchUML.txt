## QUESTION 1 — MVP: “Getting and displaying a user’s story”

### 1. Role Mapping in Your Actual Code

| **MVP Layer**                          | **Your Actual Types**                                                                                                  | **Responsibilities / Notes**                                                                                                                                                                                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Model (Application Logic + Domain)** | `StatusService` (in `src/model.service/StatusService.ts`)<br>and domain types (`Status`, `User`) from `tweeter-shared` | Encapsulates access to dummy story data; will later fetch from backend. Handles paging logic, data retrieval, and aggregation.                                                                                                                 |
| **Presenter**                          | `StoryPresenter` (in `src/presenter/StoryPresenter.ts`)                                                                | Interprets UI events from the Story view (e.g., “get next page”), validates input, manages paging state (`lastStatus`, `hasMorePages`), calls `StatusService.getStoryPage(...)`, then notifies the View.                                       |
| **View (React UI)**                    | `StoryScroller` / `StatusItemScroller` components and `useMessageList` / `useUserInfo` hooks                           | Displays the list of statuses and loading indicators. Implements the **View Interface** defined by `StoryPresenter.View`. Calls presenter methods like `loadMoreItems()` when user scrolls. Uses observer callback pattern to receive updates. |

### 2. Relationships (Dependency Rule)

* `StoryScroller` → depends on `StoryPresenter` interface only, never on services.
* `StoryPresenter` → depends on `StatusService` interface (application logic), not the UI.
* `StatusService` → depends only on domain model (`Status`, `User`), not presenters or views.
  This satisfies the **dependency inversion** rule: all dependencies flow inward toward core logic.

### 5. Why MVP Works Well Here

1. **Testability** — Logic now lives in presenters (`StoryPresenter`), which are pure TypeScript classes easily tested without rendering React.
2. **Separation of Concerns** — UI (React), coordination (Presenter), and data (Service) are isolated. Each evolves independently.
3. **Scalability & Maintainability** — Future backend integration simply swaps the dummy `StatusService` with a real one, no change to UI.

## QUESTION 2 — Template Method Pattern (Milestone 2B)

The **template method** refactor was introduced via `PagedItemPresenter.ts`, which became the shared superclass for presenters managing paging behavior (`FeedPresenter`, `FollowerPresenter`, `FolloweePresenter`, `StoryPresenter`).

---

### BEFORE UML (duplication)

Each presenter implemented its own paging logic:

```
+------------------+    +--------------------+    +--------------------+
| FeedPresenter    |    | FollowerPresenter  |    | FolloweePresenter  |
|------------------|    |--------------------|    |--------------------|
| +loadMore()      |    | +loadMore()        |    | +loadMore()        |
| +setHasMore()    |    | +setHasMore()      |    | +setHasMore()      |
| +getItems()      |    | +getItems()        |    | +getItems()        |
+------------------+    +--------------------+    +--------------------+
```

Each contained identical logic to:

* Track `lastItem`
* Call its service (`StatusService`, `FollowService`)
* Notify its view

---

### AFTER UML (with Template Method)

```
+------------------------+
| <<abstract>>           |
| PagedItemPresenter<T>  |
|------------------------|
| - lastItem: T          |
| - hasMorePages: bool   |
|------------------------|
| +loadMoreItems(): void |  <-- TEMPLATE METHOD
| +notifyView(): void    |
| #getItemsPage(): T[]   |  <-- abstract hook
+-----------^------------+
            |
     +------+------------------------------+
     |                |                    |
+-----------+   +-----------------+   +-----------------+
| FeedPresenter | | FollowerPresenter | | FolloweePresenter |
|---------------| |-----------------| |-----------------|
| #getItemsPage | | #getItemsPage  | | #getItemsPage  |
| (override)    | | (override)     | | (override)     |
+---------------+ +----------------+ +----------------+
```

**Roles:**

* **Superclass (abstract)** = `PagedItemPresenter`

  * Defines `loadMoreItems()` template algorithm:

    1. Check `hasMorePages`
    2. Call subclass-specific `getItemsPage()`
    3. Update `lastItem`, `hasMorePages`
    4. Notify view
* **Subclasses** (`FeedPresenter`, `FollowerPresenter`, etc.)

  * Implement `getItemsPage()` with their own service call (`StatusService`, `FollowService`).
  * Contain no duplicated paging logic.

---

### How Duplication Was Removed

* Before: every presenter had ~20–30 lines of identical logic (pagination, loading flags, view updates).
* After: that logic exists once in `PagedItemPresenter`.
* Subclasses now define only *what data* to load, not *how* to manage pagination.
* Result: fewer errors, simpler tests, faster future extension (e.g., adding `LikesPresenter` needs only a single override).
